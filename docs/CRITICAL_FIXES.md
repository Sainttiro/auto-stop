## v2.9.14 - Логика закрытия SHORT позиций с Multi-TP

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**При срабатывании TP для SHORT позиции система неправильно определяла тип операции!**

**Пример реального инцидента (SBER):**
```
1. Открыл SHORT 100 лотов SBER
2. Выставилось:
   - SL: 100 лотов на покупку ✅
   - TP1: 50 лотов на покупку ✅
   - TP2: 50 лотов на покупку ✅

3. Сработал TP1 → BUY 50 лотов (должно закрыть 50 лотов SHORT)
4. Система решила: "BUY + SHORT = усреднение" ❌
5. Вместо: 100 - 50 = 50 лотов
6. Сделала: 100 + 50 = 150 лотов ❌
7. Выставила новые ордера на 150 / 2 = 75 лотов каждый ❌

Результат:
- Реальная позиция: 50 лотов SHORT
- Позиция в системе: 150 лотов SHORT
- Выставлены ордера на: 75 лотов
- ПЕРЕЭКСПОЗИЦИЯ: 100 лотов! 🔴
```

### Причина

Неправильная логика определения типа операции для SHORT позиций в `position_manager.py` (строки 638-642):

```python
# НЕПРАВИЛЬНО
# Для SHORT позиции:
is_increasing = (position.direction == "SHORT" and direction == "BUY")   # ❌
is_decreasing = (position.direction == "SHORT" and direction == "SELL")  # ❌
```

**Логика SHORT позиций:**
- **Открытие SHORT** = SELL (продаешь то, чего нет)
- **Закрытие SHORT** = BUY (покупаешь обратно)
- **Усреднение SHORT** = еще SELL (продаешь еще больше)

Но код был написан наоборот!

### Исправление

Исправлена логика в `src/core/position_manager.py` (строки 638-642):

```python
# ПРАВИЛЬНО
# Для LONG позиции:
#   - BUY = увеличение (усреднение)
#   - SELL = уменьшение (закрытие)
# Для SHORT позиции:
#   - SELL = увеличение (усреднение) ← ИСПРАВЛЕНО!
#   - BUY = уменьшение (закрытие) ← ИСПРАВЛЕНО!
is_increasing = (position.direction == "LONG" and direction == "BUY") or \
               (position.direction == "SHORT" and direction == "SELL")

is_decreasing = (position.direction == "LONG" and direction == "SELL") or \
               (position.direction == "SHORT" and direction == "BUY")
```

### Последствия до исправления

- ❌ При срабатывании TP для SHORT система увеличивала позицию вместо уменьшения
- ❌ Выставлялись ордера на неправильное количество (больше чем нужно)
- ❌ Риск переэкспозиции и больших убытков
- ❌ Неправильный расчет средней цены при "усреднении"

### Как проверить

После обновления до v2.9.14+:
1. Откройте SHORT позицию с Multi-TP
2. Дождитесь срабатывания первого TP
3. Проверьте логи - должна быть запись "📉 ЗАКРЫТИЕ позиции"
4. Проверьте количество в системе - должно уменьшиться правильно

### Версии

- **Затронуты**: v1.0.0 - v2.9.13
- **Исправлено**: v2.9.14

## v2.8.7 - Дедупликация частичных исполнений

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**Вторая и последующие части частично исполненного ордера не обрабатывались!**

**Пример реального инцидента (AFKS):**
```
10:31:15 - Ордер на покупку 300 акций AFKS
10:31:15 - Часть 1: Куплено 200 акций → Обработано ✅
10:31:17 - Часть 2: Куплено 100 акций → ПРОПУЩЕНО ❌

Результат:
- Реальная позиция: 300 акций
- Позиция в системе: 200 акций
- Выставлены ордера на: 200 акций
- БЕЗ ЗАЩИТЫ: 100 акций (33%)! 🔴
```

### Причина

Недостаточно уникальный ID для частей сделки. Использовался только `order_id + timestamp`:

```python
# НЕПРАВИЛЬНО
trade_unique_id = f"{order_id}_{trade_time.timestamp()}"
```

Проблема: Если две части сделки приходят с одинаковым или очень близким timestamp, вторая часть считается дубликатом и пропускается.

### Исправление

Добавлены `quantity` и `price` в уникальный ID:

```python
# ПРАВИЛЬНО
trade_price = quotation_to_decimal(trade.price)
trade_unique_id = f"{order_id}_{trade_time.timestamp()}_{trade.quantity}_{trade_price}"
```

Теперь каждая часть сделки имеет уникальный ID, даже если приходит в одно и то же время.

### Последствия до исправления

- ❌ Часть позиции оставалась без учета в системе
- ❌ SL/TP выставлялись на неправильное количество
- ❌ При срабатывании TP закрывалось неправильное количество
- ❌ Риски рассчитывались неверно

### Как проверить

После обновления до v2.8.7+:
1. Откройте крупную позицию, которая может исполниться частями
2. Проверьте логи - должны быть записи о ВСЕХ частях исполнения
3. Проверьте количество в системе - должно совпадать с реальной позицией

### Версии

- **Затронуты**: v1.0.0 - v2.8.6
- **Исправлено**: v2.8.7

## v2.8.7 - Округление цены безубытка для Multi-TP

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**При срабатывании первого TP система не могла выставить SL в безубыток из-за неокругленной цены!**

**Пример реального инцидента (AFKS):**
```
11:53:42 - Сработал TP1, продано 100 акций
11:53:42 - Попытка выставить SL в безубыток
11:53:43 - Цена безубытка: 12.580568₽
11:53:43 - ОШИБКА: "Stop-czena dolzhna by`t` kratna minimal`nomu shagu czeny`: 0.001"
11:53:43 - SL НЕ ВЫСТАВЛЕН! ❌

Результат:
- Оставшиеся 100 акций БЕЗ ЗАЩИТЫ! 🔴
- Прибыль от TP1 под угрозой
```

### Причина

Цена безубытка рассчитывалась как `avg_price * 1.001`, но не округлялась до минимального шага цены:

```python
# НЕПРАВИЛЬНО
if position.direction == "LONG":
    breakeven_price = avg_price * Decimal('1.001')  # +0.10%
else:
    breakeven_price = avg_price * Decimal('0.999')  # -0.10%

# Цена 12.568 * 1.001 = 12.580568 ← НЕ КРАТНА 0.001!
await self.order_executor.place_stop_loss_order(
    position=position,
    stop_price=breakeven_price  # ← ОШИБКА!
)
```

### Исправление

Добавлено округление до минимального шага цены:

```python
# ПРАВИЛЬНО
from src.utils.converters import round_to_step

# Получаем минимальный шаг цены
min_price_increment, _ = await self.instrument_cache.get_price_step(position.figi)

# Расчет цены безубытка
if position.direction == "LONG":
    breakeven_price = avg_price * Decimal('1.001')  # +0.10%
else:
    breakeven_price = avg_price * Decimal('0.999')  # -0.10%

# Округляем до минимального шага цены
breakeven_price = round_to_step(breakeven_price, min_price_increment)
# 12.580568 → 12.581 ✅
```

### Последствия до исправления

- ❌ SL в безубыток не выставлялся
- ❌ Позиция оставалась без защиты после срабатывания TP
- ❌ Прибыль от первого TP под угрозой
- ❌ Риск потери всей прибыли при развороте цены

### Как проверить

После обновления до v2.8.7+:
1. Откройте позицию с Multi-TP
2. Дождитесь срабатывания первого TP
3. Проверьте логи - должна быть запись "округлено до шага X"
4. Проверьте, что SL в безубыток выставился успешно

### Версии

- **Затронуты**: v2.8.0 - v2.8.6
- **Исправлено**: v2.8.7

## v2.8.7 - Обработка ошибок при выставлении SL в безубыток

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**При ошибке выставления SL система логировала успех и оставляла позицию без защиты!**

**Что происходило:**
```
11:53:43 - Попытка выставить SL в безубыток
11:53:43 - ОШИБКА API: "Stop-czena dolzhna by`t` kratna..."
11:53:43 - Система логирует: "BREAKEVEN_SL_PLACED" ✅ ← ЛОЖЬ!
11:53:43 - Система: "✅ SL в безубыток выставлен" ← ЛОЖЬ!
11:53:43 - return ← ВЫХОД БЕЗ ЗАЩИТЫ!

Результат:
- Позиция БЕЗ стоп-лосса! 🔴
- Система думает, что всё ОК
- Нет fallback логики
```

### Причина

Отсутствовала проверка успешности выставления SL:

```python
# НЕПРАВИЛЬНО
await self.order_executor.place_stop_loss_order(
    position=position,
    stop_price=breakeven_price
)

# Логируем событие БЕЗ ПРОВЕРКИ результата!
await self.db.log_event(
    event_type="BREAKEVEN_SL_PLACED",  # ← ЛОЖЬ!
    ...
)

logger.info(f"✅ SL в безубыток выставлен")  # ← ЛОЖЬ!
return  # ← ВЫХОД, позиция БЕЗ ЗАЩИТЫ!
```

### Исправление

Добавлена проверка результата и fallback логика:

```python
# ПРАВИЛЬНО
try:
    # Выставляем SL в безубыток
    sl_order = await self.order_executor.place_stop_loss_order(
        position=position,
        stop_price=breakeven_price
    )
    
    if sl_order:
        # Успех - логируем и выходим
        await self.db.log_event(
            event_type="BREAKEVEN_SL_PLACED",
            ...
        )
        logger.info(f"✅ SL в безубыток выставлен")
        return
    else:
        # SL не выставлен - продолжаем стандартную логику
        logger.error(
            f"❌ Не удалось выставить SL в безубыток. "
            f"Продолжаем стандартную логику."
        )
        
except Exception as e:
    # Ошибка - логируем и продолжаем стандартную логику
    logger.error(
        f"❌ Ошибка при выставлении SL в безубыток: {e}. "
        f"Продолжаем стандартную логику.",
        exc_info=True
    )
    
    await self.db.log_event(
        event_type="ERROR",
        description=f"Ошибка при выставлении SL в безубыток: {str(e)}",
        ...
    )

# Если мы здесь, значит SL в безубыток не выставился
# НЕ выходим, продолжаем стандартную логику
# (код ниже отменит все ордера и выставит стандартные SL/TP)
```

### Последствия до исправления

- ❌ Критическая ошибка маскировалась как успех
- ❌ Позиция оставалась без защиты
- ❌ Нет fallback логики для повторной попытки
- ❌ Невозможно обнаружить проблему по логам

### Как проверить

После обновления до v2.8.7+:
1. Откройте позицию с Multi-TP
2. Дождитесь срабатывания первого TP
3. Проверьте логи - должна быть запись о результате выставления SL
4. Если SL не выставился, должны выставиться стандартные ордера

### Версии

- **Затронуты**: v2.8.0 - v2.8.6
- **Исправлено**: v2.8.7

## v2.8.6 - Создание позиций после срабатывания стоп-лосса

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**При срабатывании стоп-лосса система создавала новую позицию того же направления!**

**Что происходило:**
- Позиция закрывается (например, через стоп-лосс)
- Система получает уведомление о закрытии и удаляет позицию из БД
- Стоп-лосс срабатывает и создает ордер на продажу
- Система получает уведомление о новой сделке и создает новую SHORT позицию
- Новая позиция создается БЕЗ защиты (без SL/TP)

**Пример реального инцидента:**
```
13:58:02 - Продано 30 лотов MOEX (SHORT позиция закрыта)
13:59:23 - Сработал стоп-лосс, продано еще 30 лотов MOEX
          → Система СОЗДАЛА НОВУЮ SHORT позицию!
          → Выставила SL/TP на эту новую позицию
```

### Причина

В `position_manager.py` была защита от создания позиций противоположного направления сразу после закрытия, но не было защиты от создания позиций того же направления:

```python
# НЕПРАВИЛЬНО
if recently_closed:
    # Проверяем, была ли позиция закрыта недавно (в течение 5 секунд)
    time_since_close = datetime.utcnow() - recently_closed["timestamp"]
    
    if time_since_close <= timedelta(seconds=5):
        # Проверяем, не пытаемся ли мы создать позицию противоположного направления
        old_direction = recently_closed["direction"]
        new_direction = "LONG" if direction == "BUY" else "SHORT"
        
        if old_direction != new_direction:  # ← ТОЛЬКО противоположное направление!
            # Предотвращаем создание позиции
```

Это позволяло создавать новые позиции того же направления сразу после закрытия, что часто происходило при срабатывании стоп-лосса.

### Исправление

Расширена защита для блокировки ЛЮБЫХ сделок в течение 10 секунд после закрытия позиции:

```python
# ПРАВИЛЬНО
if recently_closed:
    # Проверяем, была ли позиция закрыта недавно (в течение 10 секунд)
    time_since_close = datetime.utcnow() - recently_closed["timestamp"]
    
    # ИСПРАВЛЕНИЕ: Блокируем ЛЮБЫЕ сделки в течение 10 секунд после закрытия позиции
    if time_since_close <= timedelta(seconds=10):
        # Блокируем создание ЛЮБОЙ позиции (не только противоположного направления)
        logger.warning(
            f"⚠️ ПРЕДОТВРАЩЕНО: Попытка создания {new_direction} позиции через "
            f"{time_since_close.total_seconds():.1f} сек после закрытия "
            f"{old_direction} позиции для {ticker} ({figi}). "
            f"Это может быть срабатывание стоп-лосса закрытой позиции."
        )
```

### Последствия до исправления

- ❌ Создавались новые позиции при срабатывании стоп-лосса
- ❌ Возможно создание нескольких позиций одного направления
- ❌ Риск неконтролируемых убытков при движении цены против позиции

### Как проверить

После обновления до v2.8.6+:
1. Откройте позицию и дождитесь срабатывания стоп-лосса
2. Проверьте логи - должна быть запись "ПРЕДОТВРАЩЕНО: Попытка создания позиции через X сек после закрытия"
3. Убедитесь, что новая позиция НЕ создается

### Версии

- **Затронуты**: v1.0.0 - v2.8.5
- **Исправлено**: v2.8.6

## v2.8.6 - Обработка множественных ордеров для фьючерсов

### 🔴 Критичность: ВЫСОКАЯ

### Проблема

**При покупке нескольких лотов фьючерса отдельными ордерами система не выставляла SL/TP на все лоты!**

**Пример реального инцидента:**
```
13:58:04 - Куплено 3 лота фьючерса SRZ5 (3 отдельные сделки по 1 лоту)
13:58:04 - Выставлен SL для первого лота
13:58:04 - Выставлен TP для первого лота
13:58:05 - Вторая сделка: "Все части ордера уже обработаны" ← ПРОПУЩЕНА!
13:58:05 - Третья сделка: "Все части ордера уже обработаны" ← ПРОПУЩЕНА!
```

**Результат:** SL/TP выставлены только на 1 лот из 3!

### Причина

В методе `_handle_trade` класса `TradesProcessor` было раннее завершение при `total_quantity == 0`:

```python
# НЕПРАВИЛЬНО
# Если все части уже были обработаны, выходим
if total_quantity == 0:
    logger.debug(f"Все части ордера {order_id} уже обработаны")
    return  # ← ВЫХОД БЕЗ ОБРАБОТКИ!
```

Это приводило к тому, что система пропускала обработку последующих ордеров для фьючерсов, если они имели разные order_id.

### Исправление

Удалено раннее завершение и добавлена более детальная логика обработки:

```python
# ПРАВИЛЬНО
# ИСПРАВЛЕНИЕ: Даже если все части уже обработаны, продолжаем выполнение
# для проверки позиции и выставления ордеров
if total_quantity == 0:
    if all_parts_processed:
        logger.debug(f"Все части ордера {order_id} уже обработаны, но продолжаем проверку позиции")
    else:
        logger.warning(
            f"⚠️ Странная ситуация: total_quantity=0 для ордера {order_id}, "
            f"но не все части помечены как обработанные. Продолжаем обработку."
        )
```

### Последствия до исправления

- ❌ SL/TP выставлялись только на часть позиции
- ❌ Большая часть позиции оставалась без защиты
- ❌ Риск больших убытков при движении цены против позиции

### Как проверить

## v2.1.6 - Ручные позиции без SL/TP

### 🔴 Критичность: ВЫСОКАЯ

### Проблема

**Позиции, открытые вручную через приложение Tinkoff, иногда оставались без SL/TP!**

**Что происходило:**
- Вы открываете позицию вручную через приложение Tinkoff
- API отправляет уведомление в PositionsStream
- Система получает уведомление, но **ИГНОРИРУЕТ** его
- SL/TP не выставляются
- Позиция остается без защиты

**Пример реального инцидента:**
```
1. Сработал стоп-лосс, позиция закрылась
2. Пользователь открыл новую позицию вручную
3. Система НЕ выставила SL/TP
4. Позиция осталась без защиты
```

### Причина

В методе `_process_security_position` была логика, которая игнорировала новые позиции:

```python
# НЕПРАВИЛЬНО
position = await self.position_manager.get_position(account_id, figi)
if not position:
    logger.debug(f"Позиция для {figi} не найдена в БД, пропускаем")
    return  # ← ПРОПУСКАЕМ НОВЫЕ ПОЗИЦИИ!
```

Комментарий в коде говорил:
> "Этот метод НЕ обновляет количество позиции, так как это делает поток сделок"

Но поток сделок (`TradesStream`) **НЕ ВСЕГДА** получает уведомления о ручных сделках!

### Исправление

Полностью переработан метод `_process_security_position`:

```python
# ПРАВИЛЬНО
position = await self.position_manager.get_position(account_id, figi)

# СЛУЧАЙ 1: Новая позиция (открыта вручную)
if not position and new_quantity > 0:
    # Создаем позицию в БД
    position = await self.position_manager.create_position(...)
    
    # Выставляем SL/TP
    await self._place_orders_for_position(position)
```

Теперь система:
1. Обнаруживает новые позиции через PositionsStream
2. Автоматически создает их в БД
3. Выставляет SL/TP ордера
4. Всё происходит без ручных команд

### Последствия до исправления

- ❌ Позиции, открытые вручную, оставались без защиты
- ❌ Требовалось ручное вмешательство для выставления SL/TP
- ❌ Риск больших убытков при движении цены против позиции

### Как проверить

После обновления до v2.1.6+:
1. Откройте позицию вручную через приложение Tinkoff
2. Подождите 5-10 секунд
3. Проверьте логи - должна быть запись "🆕 Обнаружена новая позиция из PositionsStream"
4. Проверьте, что SL/TP выставились автоматически

### Версии

- **Затронуты**: v1.0.0 - v2.1.5
- **Исправлено**: v2.1.6

## v2.0.10 - Ошибка datetime

### 🔴 Критичность: ВЫСОКАЯ

### Проблема

```python
AttributeError: 'datetime.datetime' object has no attribute 'ToDatetime'
```

**Что происходило:**
- Система пыталась вызвать метод `ToDatetime()` на уже конвертированном объекте datetime
- Поток обработки сделок падал при КАЖДОМ исполнении ордера
- Система переставала работать полностью

### Причина

В коде была попытка конвертировать уже конвертированный datetime:
```python
# НЕПРАВИЛЬНО
date_time = trade.date_time.ToDatetime(timezone.utc)
```

Но `trade.date_time` уже является объектом `datetime.datetime`, а не protobuf объектом.

### Исправление

```python
# ПРАВИЛЬНО
date_time = trade.date_time  # Уже datetime объект
```

### Последствия до исправления

- ❌ Система не обрабатывала ни одной сделки
- ❌ SL/TP не выставлялись
- ❌ Позиции оставались без защиты

### Версии

- **Затронуты**: v2.0.0 - v2.0.9
- **Исправлено**: v2.0.10

## v2.0.9 - Частичное исполнение ордеров

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**Система обрабатывала только ПЕРВУЮ часть частично исполненного ордера!**

**Пример реального инцидента:**
```
Ордер на покупку: 100 лотов SBER
Исполнение:
  - Часть 1: 18 лотов
  - Часть 2: 25 лотов
  - Часть 3: 30 лотов
  - Часть 4: 15 лотов
  - Часть 5: 12 лотов

Система обработала: ТОЛЬКО 18 лотов!
Фактически куплено: 100 лотов
Защищено SL/TP: 18 лотов (18%)
БЕЗ ЗАЩИТЫ: 82 лота (82%)! 🔴
```

### Причина

Использование `order_id` как уникального идентификатора сделки:

```python
# НЕПРАВИЛЬНО
trade_id = order_id  # Одинаковый для всех частей!
```

При частичном исполнении все части имеют одинаковый `order_id`, поэтому система считала, что обработала эту сделку после первой части.

### Исправление

Используется уникальный идентификатор для каждой части:

```python
# ПРАВИЛЬНО
trade_id = f"{order_id}_{datetime.utcnow().timestamp()}"
```

Теперь каждая часть имеет уникальный ID и обрабатывается отдельно.

### Последствия до исправления

- ❌ Большая часть позиции оставалась БЕЗ защиты
- ❌ При срабатывании SL закрывалась только часть позиции
- ❌ Оставшаяся часть могла уйти в большой минус
- ❌ Средняя цена рассчитывалась неправильно

### Как проверить

После обновления до v2.0.9+:
1. Откройте крупную позицию (100+ лотов)
2. Проверьте логи - должны быть записи о ВСЕХ частях исполнения
3. Проверьте количество в выставленных SL/TP - должно совпадать с полной позицией

### Версии

- **Затронуты**: v1.0.0 - v2.0.8
- **Исправлено**: v2.0.9

## v1.2.0 - Переворот позиции

### 🔴 Критичность: КРИТИЧЕСКАЯ

### Проблема

**При частичном закрытии позиции старые SL/TP ордера не отменялись!**

**Пример реального инцидента:**

```
День 1:
  - Куплено: 100 акций NLMK
  - Выставлен SL на: 100 акций

День 2:
  - Продано вручную: 80 акций
  - Осталось: 20 акций
  - Старый SL на 100 акций ОСТАЛСЯ АКТИВНЫМ! 🔴

День 3:
  - Цена упала, сработал SL на 100 акций
  - Продано: 100 акций
  - Результат: SHORT 80 акций БЕЗ защиты! 🔴
```

### Причина

Система не отслеживала уменьшение позиции и не отменяла старые ордера:

```python
# НЕПРАВИЛЬНО
# Только добавление к позиции обрабатывалось
if new_quantity > old_quantity:
    cancel_old_orders()
    place_new_orders()
# Уменьшение игнорировалось!
```

### Исправление

1. **Отслеживание изменений позиции:**
```python
# ПРАВИЛЬНО
if new_quantity != old_quantity:  # Любое изменение!
    cancel_old_orders()
    place_new_orders()
```

2. **Защита от переворота:**
```python
# В position_manager.py
if new_quantity < 0:
    logger.critical("POSITION_REVERSAL_PREVENTED")
    new_quantity = 0  # Закрыть позицию, но не переворачивать
```

### Последствия до исправления

- ❌ Старые ордера оставались активными
- ❌ Срабатывание SL создавало SHORT позиции
- ❌ SHORT позиции оставались без защиты
- ❌ Неконтролируемые убытки

### Как проверить

После обновления до v1.2.0+:
1. Откройте позицию в 100 акций
2. Частично закройте 50 акций вручную
3. Проверьте логи - должна быть запись об отмене старых ордеров
4. Проверьте новые ордера - должны быть на 50 акций

### Версии

- **Затронуты**: v1.0.0 - v1.1.2
- **Исправлено**: v1.2.0
